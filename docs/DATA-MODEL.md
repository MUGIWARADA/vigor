# Vigor — Draft Data Model (PostgreSQL)

Target schema, introduced **incrementally, as each phase needs them**. Tables marked
**✅ implemented** exist in `backend/src/main/resources/db/migration/V1__core_schema.sql` and are
enforced by Hibernate-validated JPA entities (`backend/…/domain/`); the rest are still plan. All
identifiers are surrogate `BIGINT GENERATED BY DEFAULT AS IDENTITY`, every table carries
`created_at`/`updated_at`, and foreign keys use explicit ON DELETE behaviour.

## Core reference data (Phase 2) — ✅ implemented

- **competitions** ✅ — id, name, short_name, provenance, source_name (CHECK on provenance labels)
- **seasons** ✅ — id, competition_id → competitions (RESTRICT), label, start_date, end_date,
  provenance, source_name (CHECK end_date > start_date)
- **teams** ✅ — id, name, short_name (UNIQUE), city, primary_colour, style, formation,
  provenance, source_name, source_id → import_sources (SET NULL); style CHECK-constrained to the
  four frontend styles
- **players** ✅ — id, team_id → teams (RESTRICT), full_name, position, secondary_position?,
  role, foot, dob, height_cm?, shirt_number?, provenance, source_name, source_id →
  import_sources; CHECKs for the 10 positions, 13 roles, 3 feet, sane height/shirt-number ranges
- **player_season_stats** ✅ — player_id (PK, CASCADE), 31 season aggregates (counts, xG/xA
  NUMERIC(6,2), passing/carrying/defensive splits), provenance, source_name; CHECKs keep
  completed ≤ attempted and starts ≤ appearances. **V3** adds 18 nullable dataset-v2 columns
  (tackles_won, shots_blocked, aerial splits, duels, long/short pass split, chances_created,
  carry_distance, saves, xg_prevented, penalty counts, positioning estimates) — NULL for real
  API rows (gated, honest), NULL-aware CHECKs enforce the same invariants when populated
- **player_positions** — *not implemented*: Phase 2 uses fixed `position` + `secondary_position`
  columns; history-aware positions arrive if/when multi-season player histories do

## Fixtures and participation (Phase 2) — ✅ implemented

- **matches** ✅ — id, competition_id, season_id (RESTRICT), round, kickoff TIMESTAMPTZ,
  home_team_id, away_team_id (RESTRICT), home_goals, away_goals, venue, possession_home,
  shots_home, shots_away, provenance, source_id; CHECKs for non-negative goals, possession 0–100,
  distinct teams
- **lineups** — *not implemented*: shirt numbers/lineup sheets arrive with Phase 6 match-module
  persistence
- **player_match_minutes** ✅ — id, match_id (CASCADE), player_id (CASCADE),
  UNIQUE (match_id, player_id), minutes, starter, rating NUMERIC(3,1), provenance
- **match_events** ✅ — id, match_id (CASCADE), minute, type, team_id (RESTRICT), player_id
  (SET NULL), secondary_player_id (SET NULL), x, y, end_x, end_y NUMERIC(5,2), value
  NUMERIC(5,2), note, provenance, source_id; CHECKs: 12 event types (incl. 'pass',
  'incomplete-pass'), minute 1–130, x/y/end_x/end_y 0–100, value 0–1, two-point types must carry
  both end coordinates; index (match_id, minute)
- **import_sources** ✅ — id, name, version, licence_note; empty in Phase 2 (mechanism ready for
  the Phase 4 import pipeline; imported rows will carry provenance 'IMPORTED' + source_id)
- **possessions** — *deferred*: sequence-level possession phases are a Phase 6 analysis input

## Conventions

- Provenance columns (`provenance`, `source_name`, `import_batch_id`, `model_version`) on every
  data table — mirrors the frontend's six provenance labels.
- Indexes: foreign keys, `(player_id, season_id)` on metric_results, `(match_id, minute)` on events,
  full-text or trigram index on players.full_name for search.
- No metric value is ever stored as `0` to mean "missing" — missing values are NULL and surfaced as
  unavailable in the API and UI.
- Events tables (Phase 3/4): **player_events** — id, match_id, minute, second, event_type, team_id,
  player_id?, secondary_player_id?, x, y, end_x?, end_y?, value?, body_part?, provenance, verified_at?
